# Deep Dive: Internationalization (i18n), `Intl`, Plural Rules, RTL

> Terkait: [02 HTML](../roadmap/02-html.md), [03 CSS](../roadmap/03-css.md). Deep dive lain:
> [Accessibility tree](accessibility-tree.md), [CSS Cascade & Specificity](css-cascade.md)

## Pertanyaan pembuka

Situs ini sudah dua bahasa. Apakah itu berarti sudah ter-internasionalisasi? Coba pikirkan: kenapa
`n === 1 ? "file" : "files"` benar untuk bahasa Inggris tapi salah untuk bahasa Rusia di angka 21? Kenapa
`"Zoë" < "apple"` bernilai `true`? Kenapa memotong nama pengguna dengan `slice(0, 10)` bisa
memotong emoji keluarga menjadi satu orang saja? Kenapa `new Date("2026-11-24")` di Jakarta
menunjukkan pukul 07.00? Dan apa yang terjadi pada `margin-left` saat halaman dibalik untuk bahasa Arab?

## Model mental

Ada dua istilah yang sering tertukar:

- **Internationalization (i18n):** membuat kode **tidak berasumsi** pada satu bahasa, budaya, atau
  arah tulisan. Ini pekerjaan engineering, dilakukan sekali.
- **Localization (l10n):** mengisi kode itu dengan terjemahan dan format untuk satu **locale**
  tertentu. Ini pekerjaan konten, dilakukan per bahasa.

Locale bukan hanya bahasa. Tag BCP 47 seperti `id-ID`, `en-US`, `pt-BR`, `zh-Hant-TW`, atau
`ar-EG-u-nu-latn` menggabungkan bahasa, aksara, wilayah, dan ekstensi (misalnya sistem angka).
Wilayah menentukan format angka dan tanggal; bahasa menentukan kata dan aturan plural.

Hampir setiap bug i18n berasal dari satu dari lima asumsi yang diam-diam berbahasa Inggris:

| Asumsi | Kenyataan | Alat yang benar |
| --- | --- | --- |
| angka ditulis `1,234.5` | `1.234,5` (id), `12,34,567` (hi), `١٬٢٣٤` (ar) | `Intl.NumberFormat` |
| plural = 1 vs banyak | 1 bentuk (id, ja) sampai 6 bentuk (ar, cy) | `Intl.PluralRules`, ICU MessageFormat |
| urutan huruf = urutan kode Unicode | `ä` disortir beda di Jerman dan Swedia | `Intl.Collator` |
| satu karakter = satu `char` | emoji, aksen gabungan, aksara tanpa spasi | `Intl.Segmenter`, `normalize()` |
| tulisan dari kiri ke kanan | arab, ibrani, persia, urdu ditulis kanan ke kiri | `dir`, CSS logical properties |

## Mekanisme detail

### 1. `Intl`: data CLDR di dalam browser

`Intl` adalah API bawaan JavaScript (spesifikasi ECMA-402) yang memakai data **CLDR** (Unicode
Common Locale Data Repository). Browser dan Node sudah membawa data itu lewat ICU, jadi kamu tidak
perlu library untuk format dasar:

| API | Kegunaan |
| --- | --- |
| `NumberFormat` | angka, mata uang, persen, satuan, notasi ringkas (`1,3 jt`) |
| `DateTimeFormat` | tanggal dan jam, termasuk zona waktu dan kalender |
| `RelativeTimeFormat` | "kemarin", "dalam 3 hari" |
| `ListFormat` | "React, Vue, dan Svelte" |
| `PluralRules` | kategori plural untuk sebuah angka |
| `Collator` | perbandingan string untuk sorting dan pencarian |
| `Segmenter` | memecah teks menjadi grapheme, kata, atau kalimat |
| `DisplayNames` | nama bahasa, wilayah, mata uang dalam bahasa lain |

Satu aturan kinerja: membuat formatter itu mahal karena harus memuat data locale, sedangkan
memanggil `.format()` murah. **Buat formatter sekali dan pakai ulang**, jangan di dalam loop render.

### 2. Plural rules: kategori, bukan angka

CLDR membagi angka ke enam kategori: `zero`, `one`, `two`, `few`, `many`, `other`. Setiap bahasa
memakai subset yang berbeda dengan aturan yang berbeda. Bahasa Indonesia hanya punya `other`
(kata benda tidak berubah: "1 file", "5 file"). Bahasa Inggris punya `one` dan `other`. Bahasa
Rusia memakai `one` untuk 1, 21, 31 (tapi bukan 11), `few` untuk 2–4, 22–24, dan `many` untuk
sisanya. Bahasa Arab memakai keenamnya.

Karena itu, string terjemahan tidak boleh berbentuk "teks + angka + `s`". Formatnya harus bisa
memuat semua kategori. Standar de facto adalah **ICU MessageFormat** (dipakai FormatJS/react-intl,
i18next dengan plugin ICU, Lingui, dan dasar dari MessageFormat 2.0 di Unicode):

```
{count, plural,
  =0 {Keranjang kosong}
  other {# barang di keranjang}
}
```

Terjemahan bahasa Rusia untuk pesan yang sama akan punya cabang `one`, `few`, `many`, dan `other`.
Kode aplikasi tidak berubah; hanya file pesannya.

Ada juga plural **ordinal** (`type: "ordinal"`): bahasa Inggris memakai `1st`, `2nd`, `3rd`, `4th`,
tapi `11th`, `12th`, `13th`. Aturan itu juga ada di CLDR, bukan di kode kita.

### 3. Teks bukan array karakter

String JavaScript adalah urutan **unit kode UTF-16**. Satu hal yang dilihat pengguna sebagai satu
huruf (*grapheme cluster*) bisa terdiri dari beberapa code point, dan satu code point bisa terdiri
dari dua unit kode:

- `length` menghitung unit UTF-16. `[...s]` menghitung code point. `Intl.Segmenter` dengan
  `granularity: "grapheme"` menghitung yang dilihat manusia.
- `"é"` bisa ditulis sebagai satu code point (U+00E9) atau `e` + aksen gabungan (U+0301).
  Tampilannya sama, tapi `===` bernilai `false`. Normalisasi dengan `normalize("NFC")` sebelum
  membandingkan atau menyimpan.
- Bahasa seperti Jepang, Thai, dan Tionghoa tidak memakai spasi di antara kata. `split(" ")` tidak
  berguna; `Intl.Segmenter` dengan `granularity: "word"` memakai kamus untuk memecahnya.
- Huruf besar dan kecil bergantung bahasa. Dalam bahasa Turki, `i` kecil menjadi `İ` (bertitik)
  dan `I` besar menjadi `ı` (tanpa titik). Pakai `toLocaleUpperCase(locale)`, dan di HTML pasang
  `lang` supaya CSS `text-transform` ikut benar.

### 4. Sorting dan pencarian

`Array.prototype.sort()` tanpa argumen membandingkan unit kode UTF-16, jadi semua huruf besar ada
sebelum semua huruf kecil dan huruf beraksen berada di akhir. `Intl.Collator` menerapkan aturan
pengurutan per bahasa (*Unicode Collation Algorithm* dengan tailoring CLDR). Di Jerman `ä`
disortir dekat `a`; di Swedia `å`, `ä`, `ö` adalah huruf terpisah di akhir alfabet. Opsi yang
berguna:

- `numeric: true`: `item9` sebelum `item10`.
- `sensitivity: "base"`: pencarian yang tidak peduli huruf besar dan aksen (`"cafe"` cocok dengan
  `"Café"`).

### 5. Tanggal, waktu, dan zona waktu

`Date` menyimpan satu titik waktu dalam milidetik sejak epoch UTC. Ia tidak menyimpan zona waktu.
Zona hanya muncul saat **mem-parse** dan **menampilkan**:

- `new Date("2026-11-24")` (hanya tanggal) di-parse sebagai **UTC**, sedangkan
  `new Date("2026-11-24T00:00")` (tanggal + jam tanpa offset) di-parse sebagai **waktu lokal**.
  Ini aturan spesifikasi, dan sumber bug "tanggal mundur satu hari" yang klasik.
- Simpan dan kirim waktu sebagai ISO 8601 dengan offset (`2026-11-24T23:30:00Z`), lalu tampilkan
  dengan `timeZone` yang jelas. Indonesia saja punya tiga zona (WIB, WITA, WIT).
- Tanggal ulang tahun atau tanggal jatuh tempo sering kali **bukan** titik waktu, melainkan tanggal
  kalender. Simpan sebagai string `YYYY-MM-DD`, bukan `Date`. `Temporal.PlainDate` dibuat untuk
  kasus ini; `Temporal` sedang dirilis bertahap di browser, jadi periksa dukungannya dulu.

### 6. Arah tulisan: `dir`, bidi, dan logical properties

Untuk bahasa yang ditulis kanan ke kiri (RTL), atribut `dir="rtl"` di `<html>` membalik arah
*inline*: teks rata kanan, kolom flex dan grid berurutan dari kanan, scrollbar pindah ke kiri.
Tapi CSS yang memakai arah **fisik** (`left`, `right`, `margin-left`, `padding-right`) tidak ikut
terbalik, karena "kiri" tetap kiri.

CSS **logical properties** mengganti arah fisik dengan arah relatif terhadap tulisan:

| Fisik | Logis |
| --- | --- |
| `margin-left` / `margin-right` | `margin-inline-start` / `margin-inline-end` |
| `padding-left` | `padding-inline-start` |
| `left` / `right` (positioning) | `inset-inline-start` / `inset-inline-end` |
| `text-align: left` | `text-align: start` |
| `border-top-left-radius` | `border-start-start-radius` |
| `width` / `height` | `inline-size` / `block-size` |

Hal lain yang perlu dibalik di RTL: ikon berarah (panah "berikutnya", ikon kirim), lewat selector
`:dir(rtl)`. Yang **tidak** dibalik: logo, ikon putar media, grafik waktu, dan angka.

Di dalam teks, algoritma **bidi** Unicode mengatur campuran kanan-ke-kiri dan kiri-ke-kanan dalam
satu baris. Nilai yang datang dari pengguna (nama, judul) sebaiknya dibungkus `<bdi>` atau diberi
`dir="auto"`, supaya arahnya tidak "bocor" ke tanda baca di sekitarnya.

### 7. Atribut `lang` lebih penting dari kelihatannya

`<html lang="id">` bukan hiasan. Atribut ini menentukan:

- **pelafalan screen reader** (lihat [deep dive Accessibility tree](accessibility-tree.md));
  bagian berbahasa lain perlu `lang` sendiri, misalnya `<span lang="en">deep dive</span>`;
- **`text-transform`**, pemenggalan kata (`hyphens: auto`), dan pemilihan glyph font untuk aksara
  yang sama (Tionghoa sederhana, tradisional, dan Jepang memakai bentuk berbeda);
- **tawaran terjemahan otomatis** di browser dan **mesin pencari**, bersama
  `<link rel="alternate" hreflang="en" href="...">` untuk halaman versi bahasa lain.

### 8. Arsitektur terjemahan di aplikasi

Beberapa keputusan yang lebih sulit diubah belakangan:

- **Kunci pesan:** kunci semantik (`cart.empty`) lebih stabil daripada kalimat sumber sebagai
  kunci, karena perbaikan typo di bahasa sumber tidak membatalkan semua terjemahan.
- **Jangan menyambung potongan kalimat.** `t("hello") + name + t("welcome")` mengunci urutan kata
  bahasa sumber. Pakai placeholder: `"Halo {name}, selamat datang"`.
- **Muat pesan per locale dan per rute**, bukan semua bahasa dalam satu bundle.
- **Sediakan ruang.** Teks bahasa Jerman atau Finlandia bisa 30–40% lebih panjang dari bahasa
  Inggris. *Pseudo-localization* (`[Ḱéŕàñĵàñĝ ķöšöñĝ !!!]`) membantu menemukan teks yang belum
  diterjemahkan dan layout yang patah, sebelum penerjemah bekerja.
- **Tentukan locale dengan urutan yang jelas:** pilihan eksplisit pengguna, lalu URL (`/en/...`),
  lalu `Accept-Language` atau `navigator.languages`, lalu default. Jangan menebak dari alamat IP.

**2. Plural rules dan bug "1 vs banyak".**

```js
const counts = [0, 1, 2, 3, 5, 11, 21, 100, 1.5];
for (const locale of ["id", "en", "ru", "ar", "pl", "cy"]) {
  const pr = new Intl.PluralRules(locale);
  const cats = pr.resolvedOptions().pluralCategories;
  console.log(locale.padEnd(3), cats.join("/").padEnd(32), counts.map((c) => `${c}:${pr.select(c)}`).join(" "));

// Bug klasik: n === 1 ? "file" : "files"
const naive = (n) => `${n} ${n === 1 ? "файл" : "файла"}`;

const pr = new Intl.PluralRules("ru");
const proper = (n) => `${n} ${forms[pr.select(n)]}`;

console.log("---");
```

**3. Sorting, panjang string, dan segmentasi.**

```js
// Sorting
const names = ["Zoë", "zebra", "Émile", "apple", "Ähre", "Østen", "item10", "item9"];
console.log("sort()          :", [...names].sort().join(", "));
console.log("Collator de     :", [...names].sort(new Intl.Collator("de").compare).join(", "));
console.log("Collator sv     :", [...names].sort(new Intl.Collator("sv").compare).join(", "));
console.log("numeric: true   :", ["item10", "item9", "item1"].sort(new Intl.Collator("en", { numeric: true }).compare).join(", "));
console.log("---");
// Panjang string dan potong teks
const s = "👨‍👩‍👧 Halo 🇮🇩 é";
console.log("length:", s.length, "| [...s]:", [...s].length,
  "| grapheme:", [...new Intl.Segmenter("id", { granularity: "grapheme" }).segment(s)].length);
console.log("slice(0, 2):", JSON.stringify(s.slice(0, 2)));
const cafe1 = "café", cafe2 = "café";
console.log(cafe1, cafe2, "===", cafe1 === cafe2, "| NFC ===", cafe1.normalize("NFC") === cafe2.normalize("NFC"), "| length", cafe1.length, cafe2.length);
console.log("---");
// Pemotongan kata untuk bahasa tanpa spasi
const ja = "私はフロントエンドを勉強しています";
console.log([...new Intl.Segmenter("ja", { granularity: "word" }).segment(ja)].filter((x) => x.isWordLike).map((x) => x.segment).join(" | "));
console.log("---");
// Case mapping bergantung locale
console.log("I".toLowerCase(), "I".toLocaleLowerCase("tr"), "i".toUpperCase(), "i".toLocaleUpperCase("tr"), "ß".toUpperCase());
```

- `sort()` biasa menaruh `Zoë` sebelum `apple` (huruf besar lebih dulu di tabel Unicode) dan
  semua huruf beraksen di akhir. `Collator` Jerman dan Swedia tidak sepakat soal `Ä` dan `Ø`.
- String yang tampak 10 "huruf" punya `length` 20. `slice(0, 2)` memotong emoji keluarga dan
  hanya menyisakan ayahnya.
- Dua `café` yang terlihat sama tidak `===` sebelum dinormalisasi.
- Kalimat Jepang tanpa spasi dipecah menjadi kata oleh `Segmenter`.
- `"ß".toUpperCase()` menjadi dua huruf (`SS`), jadi panjang string bisa berubah setelah
  mengubah huruf besar.

**4. RTL, logical properties, dan `lang` di Chromium.**

```js
const { chromium } = require("playwright");
(async () => {
  const browser = await chromium.launch();
  const page = await browser.newPage({ viewport: { width: 400, height: 300 } });
  await page.setContent(`<!doctype html><style>
    body { margin: 0; font: 16px sans-serif; }
    .card { width: 300px; border: 1px solid; }
    .fisik  { margin-left: 40px; padding-left: 8px; text-align: left; }
    .logis  { margin-inline-start: 40px; padding-inline-start: 8px; text-align: start; }
    .panah { display: inline-block; }  /* transform tidak berlaku di elemen inline biasa */
    .panah:dir(rtl) { transform: scaleX(-1); }
  </style>
  <div dir="ltr"><div class="card fisik" id="ltr-fisik">Kartu</div><div class="card logis" id="ltr-logis">Kartu</div></div>
  <div dir="rtl" lang="ar"><div class="card fisik" id="rtl-fisik">بطاقة</div><div class="card logis" id="rtl-logis">بطاقة</div>
    <span class="panah" id="panah">→</span></div>
  <p lang="tr" id="tr" style="text-transform: uppercase">istanbul</p>
  <p lang="en" id="en" style="text-transform: uppercase">istanbul</p>`);
  const out = await page.evaluate(() => {
    const box = (id) => {
      const el = document.getElementById(id), r = el.getBoundingClientRect(), cs = getComputedStyle(el);
      return `left=${r.left} right=${400 - r.right} textAlign=${cs.textAlign} direction=${cs.direction}`;
    };
    return {
      "ltr fisik": box("ltr-fisik"), "ltr logis": box("ltr-logis"),
      "rtl fisik": box("rtl-fisik"), "rtl logis": box("rtl-logis"),
      panah: getComputedStyle(document.getElementById("panah")).transform,
    };
  });
  console.log(out);
  // innerText mengikuti text-transform, jadi hasil uppercase per bahasa terlihat langsung.
  console.log("tr:", await page.locator("#tr").innerText(), "| en:", await page.locator("#en").innerText());
  await browser.close();
})();
```

```
  panah: 'matrix(-1, 0, 0, 1, 0, 0)'
}
tr: İSTANBUL | en: ISTANBUL
```

Di LTR, kartu fisik dan kartu logis berada di posisi yang sama. Di RTL, kartu logis berpindah ke
kanan dengan jarak 40 px dari tepi kanan, persis seperti cerminan. Kartu fisik menempel di tepi
kanan tanpa jarak, sementara `margin-left` 40 px-nya tidak berpengaruh, dan teksnya tetap rata kiri.
Panah mendapat `scaleX(-1)` hanya karena berada di dalam `dir="rtl"`. Paragraf yang sama menjadi
`İSTANBUL` dengan `lang="tr"` dan `ISTANBUL` dengan `lang="en"`.

Catat hasil dan kejutannya di [catatan eksperimen](/notes/). Tantangan berikutnya: tambahkan
`dir="rtl"` ke `<html>` di situs ini lewat DevTools, lalu cari komponen mana yang masih memakai
arah fisik.

## Implikasi praktis

- **Jangan pernah memformat angka, mata uang, atau tanggal dengan tangan.** Pakai `Intl`, dan buat
  formatter sekali per locale.
- **Pesan terjemahan harus mendukung semua kategori plural.** Pakai ICU MessageFormat, bukan
  `count === 1`.
- **Sortir dengan `Intl.Collator`**, dan bandingkan string setelah `normalize("NFC")`.
- **Potong dan hitung teks per grapheme** (`Intl.Segmenter`), terutama untuk batas karakter input
  dan nama pengguna.
- **Kirim dan simpan waktu sebagai ISO 8601 dengan offset;** tanggal kalender sebagai `YYYY-MM-DD`.
  Selalu sebut `timeZone` saat menampilkan.
- **Tulis CSS dengan logical properties sejak awal.** Mengubahnya belakangan jauh lebih mahal
  daripada memulai dengannya.
- **Pasang `lang` di `<html>` dan di setiap potongan berbahasa lain,** dan `dir` untuk RTL. Bungkus
  input pengguna dengan `<bdi>` atau `dir="auto"`.
- **Uji dengan pseudo-localization dan satu locale RTL** di CI atau Storybook, bukan setelah
  penerjemah selesai.
