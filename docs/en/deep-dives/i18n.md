# Deep Dive: Internationalization (i18n), `Intl`, Plural Rules, RTL

> Related: [02 HTML](../roadmap/02-html.md), [03 CSS](../roadmap/03-css.md). Other deep dives:
> [The accessibility tree](accessibility-tree.md), [CSS Cascade & Specificity](css-cascade.md)

## Opening questions

This site is already bilingual. Does that mean it's internationalized? Think about it: why is
`n === 1 ? "file" : "files"` right for English but wrong for Russian at 21? Why is
`"Zoë" < "apple"` `true`? Why can trimming a username with `slice(0, 10)` cut a family emoji down to
a single person? Why does `new Date("2026-11-24")` show 07:00 in Jakarta? And what happens to
`margin-left` when the page is flipped for Arabic?

## Mental model

Two terms often get mixed up:

- **Internationalization (i18n):** making code **assume nothing** about one language, culture, or
  writing direction. Engineering work, done once.
- **Localization (l10n):** filling that code with translations and formats for one particular
  **locale**. Content work, done per language.

A locale is more than a language. BCP 47 tags like `id-ID`, `en-US`, `pt-BR`, `zh-Hant-TW`, or
`ar-EG-u-nu-latn` combine language, script, region, and extensions (such as the numbering system).
The region decides number and date formats; the language decides words and plural rules.

Almost every i18n bug comes from one of five assumptions that are quietly English:

| Assumption | Reality | The right tool |
| --- | --- | --- |
| numbers are written `1,234.5` | `1.234,5` (id), `12,34,567` (hi), `١٬٢٣٤` (ar) | `Intl.NumberFormat` |
| plural = one vs many | from 1 form (id, ja) up to 6 forms (ar, cy) | `Intl.PluralRules`, ICU MessageFormat |
| alphabetical order = Unicode code order | `ä` sorts differently in German and Swedish | `Intl.Collator` |
| one character = one `char` | emoji, combining accents, scripts without spaces | `Intl.Segmenter`, `normalize()` |
| text runs left to right | Arabic, Hebrew, Persian, Urdu run right to left | `dir`, CSS logical properties |

## Detailed mechanism

### 1. `Intl`: CLDR data inside the browser

`Intl` is JavaScript's built-in API (the ECMA-402 specification) backed by **CLDR** data (the
Unicode Common Locale Data Repository). Browsers and Node ship that data via ICU, so you don't need
a library for basic formatting:

| API | Purpose |
| --- | --- |
| `NumberFormat` | numbers, currency, percent, units, compact notation (`1.3M`) |
| `DateTimeFormat` | dates and times, including time zones and calendars |
| `RelativeTimeFormat` | "yesterday", "in 3 days" |
| `ListFormat` | "React, Vue, and Svelte" |
| `PluralRules` | the plural category for a number |
| `Collator` | string comparison for sorting and searching |
| `Segmenter` | splitting text into graphemes, words, or sentences |
| `DisplayNames` | names of languages, regions, currencies in another language |

One performance rule: creating a formatter is expensive because it loads locale data, while calling
`.format()` is cheap. **Create formatters once and reuse them**, not inside a render loop.

### 2. Plural rules: categories, not numbers

CLDR sorts numbers into six categories: `zero`, `one`, `two`, `few`, `many`, `other`. Each language
uses a different subset with different rules. Indonesian has only `other` (nouns don't change:
"1 file", "5 file"). English has `one` and `other`. Russian uses `one` for 1, 21, 31 (but not 11),
`few` for 2–4, 22–24, and `many` for the rest. Arabic uses all six.

So translated strings can't be "text + number + `s`". The format has to hold every category. The de
facto standard is **ICU MessageFormat** (used by FormatJS/react-intl, i18next with the ICU plugin,
Lingui, and the basis of Unicode's MessageFormat 2.0):

```
{count, plural,
  =0 {Your cart is empty}
  one {# item in your cart}
  other {# items in your cart}
}
```

The Russian translation of the same message has `one`, `few`, `many`, and `other` branches. The
application code doesn't change; only the message file does.

There are also **ordinal** plurals (`type: "ordinal"`): English uses `1st`, `2nd`, `3rd`, `4th`, but
`11th`, `12th`, `13th`. Those rules live in CLDR too, not in our code.

### 3. Text is not an array of characters

A JavaScript string is a sequence of **UTF-16 code units**. What a user sees as one letter (a
*grapheme cluster*) can be several code points, and one code point can be two code units:

- `length` counts UTF-16 units. `[...s]` counts code points. `Intl.Segmenter` with
  `granularity: "grapheme"` counts what humans see.
- `"é"` can be written as one code point (U+00E9) or as `e` + a combining accent (U+0301). They look
  the same, but `===` is `false`. Normalize with `normalize("NFC")` before comparing or storing.
- Languages like Japanese, Thai, and Chinese don't put spaces between words. `split(" ")` is
  useless; `Intl.Segmenter` with `granularity: "word"` uses a dictionary to split them.
- Upper and lower case depend on the language. In Turkish, lowercase `i` becomes `İ` (dotted) and
  uppercase `I` becomes `ı` (dotless). Use `toLocaleUpperCase(locale)`, and set `lang` in HTML so
  CSS `text-transform` gets it right too.

### 4. Sorting and searching

`Array.prototype.sort()` without an argument compares UTF-16 code units, so every uppercase letter
comes before every lowercase one and accented letters end up at the end. `Intl.Collator` applies
per-language ordering (the *Unicode Collation Algorithm* with CLDR tailorings). In German `ä` sorts
near `a`; in Swedish `å`, `ä`, `ö` are separate letters at the end of the alphabet. Useful options:

- `numeric: true`: `item9` before `item10`.
- `sensitivity: "base"`: searching that ignores case and accents (`"cafe"` matches `"Café"`).

### 5. Dates, times, and time zones

A `Date` stores one point in time as milliseconds since the UTC epoch. It stores no time zone. Zones
only come in when **parsing** and **displaying**:

- `new Date("2026-11-24")` (date only) is parsed as **UTC**, while `new Date("2026-11-24T00:00")`
  (date + time without an offset) is parsed as **local time**. That's the spec, and the source of
  the classic "date is off by one day" bug.
- Store and send times as ISO 8601 with an offset (`2026-11-24T23:30:00Z`), then display them with
  an explicit `timeZone`. Indonesia alone has three zones (WIB, WITA, WIT).
- Birthdays and due dates are often **not** points in time but calendar dates. Store them as a
  `YYYY-MM-DD` string, not a `Date`. `Temporal.PlainDate` was made for this; `Temporal` is rolling
  out gradually in browsers, so check support first.

### 6. Writing direction: `dir`, bidi, and logical properties

For right-to-left (RTL) languages, `dir="rtl"` on `<html>` flips the *inline* direction: text aligns
right, flex and grid items run from the right, the scrollbar moves to the left. But CSS written with
**physical** directions (`left`, `right`, `margin-left`, `padding-right`) doesn't flip, because
"left" is still left.

CSS **logical properties** replace physical directions with directions relative to the writing
mode:

| Physical | Logical |
| --- | --- |
| `margin-left` / `margin-right` | `margin-inline-start` / `margin-inline-end` |
| `padding-left` | `padding-inline-start` |
| `left` / `right` (positioning) | `inset-inline-start` / `inset-inline-end` |
| `text-align: left` | `text-align: start` |
| `border-top-left-radius` | `border-start-start-radius` |
| `width` / `height` | `inline-size` / `block-size` |

Other things to flip in RTL: directional icons ("next" arrows, the send icon), via the `:dir(rtl)`
selector. Things **not** to flip: logos, media play icons, time charts, and numbers.

Within text, the Unicode **bidi** algorithm handles mixing right-to-left and left-to-right in one
line. Values coming from users (names, titles) should be wrapped in `<bdi>` or given `dir="auto"`,
so their direction doesn't "leak" into the surrounding punctuation.

### 7. The `lang` attribute matters more than it looks

`<html lang="en">` isn't decoration. It decides:

- **screen reader pronunciation** (see the [accessibility tree deep dive](accessibility-tree.md));
  parts in another language need their own `lang`, for example `<span lang="id">belajar</span>`;
- **`text-transform`**, hyphenation (`hyphens: auto`), and font glyph selection for shared scripts
  (Simplified Chinese, Traditional Chinese, and Japanese use different forms);
- **automatic translation offers** in the browser and **search engines**, together with
  `<link rel="alternate" hreflang="id" href="...">` for the other-language versions of a page.

### 8. Translation architecture in an app

A few decisions that are harder to change later:

- **Message keys:** semantic keys (`cart.empty`) are more stable than using the source sentence as
  the key, because fixing a typo in the source language doesn't invalidate every translation.
- **Don't concatenate sentence fragments.** `t("hello") + name + t("welcome")` locks in the source
  language's word order. Use placeholders: `"Hello {name}, welcome"`.
- **Load messages per locale and per route**, not every language in one bundle.
- **Leave room.** German or Finnish text can be 30–40% longer than English. *Pseudo-localization*
  (`[Ýöûŕ çàŕţ îš éɱþţý !!!]`) helps find untranslated strings and broken layouts before translators
  start.
- **Pick the locale in a clear order:** the user's explicit choice, then the URL (`/en/...`), then
  `Accept-Language` or `navigator.languages`, then a default. Don't guess from the IP address.

## Experiments

Experiments 1 to 3 run on Node 22 (ICU 77.1, Unicode 16) with `TZ=Asia/Jakarta`. Experiment 4 needs
real layout, so it runs in Chromium via Playwright. All output is real; other ICU versions may
differ slightly (for example in spacing or abbreviations).

**1. One number, one date, six locales.**

```js
const n = 1234567.891;
const d = new Date(Date.UTC(2026, 10, 24, 1, 30));
for (const locale of ["id-ID", "en-US", "de-DE", "ar-EG", "hi-IN", "ja-JP"]) {
  const num = new Intl.NumberFormat(locale).format(n);
  const money = new Intl.NumberFormat(locale, { style: "currency", currency: "IDR" }).format(n);
  const date = new Intl.DateTimeFormat(locale, { dateStyle: "medium", timeStyle: "short", timeZone: "Asia/Jakarta" }).format(d);
  console.log(locale.padEnd(6), "|", num.padEnd(14), "|", money.padEnd(18), "|", date);
}
console.log("---");
const rtf = new Intl.RelativeTimeFormat("id", { numeric: "auto" });
console.log([-1, 0, 1, 3].map((x) => rtf.format(x, "day")));
console.log(new Intl.ListFormat("id", { type: "conjunction" }).format(["React", "Vue", "Svelte"]));
console.log(new Intl.ListFormat("en", { type: "conjunction" }).format(["React", "Vue", "Svelte"]));
console.log(new Intl.NumberFormat("id", { notation: "compact" }).format(1_250_000), new Intl.NumberFormat("en", { notation: "compact" }).format(1_250_000));
console.log("---");
// Time: strings without a time zone, and one instant in several zones
console.log(new Date("2026-11-24").toISOString(), "|", new Date("2026-11-24T00:00").toISOString());
const flight = new Date("2026-11-24T23:30:00Z");
for (const tz of ["Asia/Jakarta", "Asia/Jayapura", "America/Los_Angeles"])
  console.log(tz.padEnd(20), new Intl.DateTimeFormat("id", { dateStyle: "full", timeStyle: "short", timeZone: tz }).format(flight));
```

Worth noticing:

- Thousands and decimal separators swap between `id-ID` and `en-US`. `hi-IN` groups digits in twos
  after the thousands (`12,34,567`, the lakh system). `ar-EG` uses Arabic-Indic digits and invisible
  direction control characters.
- Rupiah shows two decimals because that's IDR's official *minor unit* in ISO 4217, even though it's
  rarely used in practice. Add `maximumFractionDigits: 0` if that's what the product wants.
- **`new Date("2026-11-24")` becomes midnight UTC**, which is 07:00 in Jakarta (WIB), while
  `new Date("2026-11-24T00:00")` becomes midnight WIB, which is 17:00 UTC the day before.
- The same flight is already on the 25th in Jakarta and Jayapura but still on the 24th in Los
  Angeles. (The output is in Indonesian: *Rabu* = Wednesday, *Selasa* = Tuesday, *pukul* = at.)

**2. Plural rules and the "one vs many" bug.**

```js
const counts = [0, 1, 2, 3, 5, 11, 21, 100, 1.5];
for (const locale of ["id", "en", "ru", "ar", "pl", "cy"]) {
  const pr = new Intl.PluralRules(locale);
  const cats = pr.resolvedOptions().pluralCategories;
  console.log(locale.padEnd(3), cats.join("/").padEnd(32), counts.map((c) => `${c}:${pr.select(c)}`).join(" "));
}
console.log("---");
// The classic bug: n === 1 ? "file" : "files"
const naive = (n) => `${n} ${n === 1 ? "файл" : "файла"}`;
const forms = { one: "файл", few: "файла", many: "файлов", other: "файла" };
const pr = new Intl.PluralRules("ru");
const proper = (n) => `${n} ${forms[pr.select(n)]}`;
for (const n of [1, 2, 5, 21, 25]) console.log(String(n).padEnd(3), "naif:", naive(n).padEnd(10), "benar:", proper(n));
console.log("---");
const ord = new Intl.PluralRules("en", { type: "ordinal" });
const suffix = { one: "st", two: "nd", few: "rd", other: "th" };
console.log([1, 2, 3, 4, 11, 12, 13, 21, 22, 23, 101, 111].map((n) => n + suffix[ord.select(n)]).join(" "));
```

category in Arabic and Welsh.

**3. Sorting, string length, and segmentation.**

```js
// Sorting
const names = ["Zoë", "zebra", "Émile", "apple", "Ähre", "Østen", "item10", "item9"];
console.log("sort()          :", [...names].sort().join(", "));
console.log("Collator de     :", [...names].sort(new Intl.Collator("de").compare).join(", "));
console.log("Collator sv     :", [...names].sort(new Intl.Collator("sv").compare).join(", "));
console.log("numeric: true   :", ["item10", "item9", "item1"].sort(new Intl.Collator("en", { numeric: true }).compare).join(", "));
console.log("---");
// String length and truncation
const s = "👨‍👩‍👧 Halo 🇮🇩 é";
console.log("length:", s.length, "| [...s]:", [...s].length,
  "| grapheme:", [...new Intl.Segmenter("id", { granularity: "grapheme" }).segment(s)].length);
console.log("slice(0, 2):", JSON.stringify(s.slice(0, 2)));
const cafe1 = "café", cafe2 = "café";
console.log(cafe1, cafe2, "===", cafe1 === cafe2, "| NFC ===", cafe1.normalize("NFC") === cafe2.normalize("NFC"), "| length", cafe1.length, cafe2.length);
console.log("---");
// Word segmentation for a language without spaces
const ja = "私はフロントエンドを勉強しています";
console.log([...new Intl.Segmenter("ja", { granularity: "word" }).segment(ja)].filter((x) => x.isWordLike).map((x) => x.segment).join(" | "));
console.log("---");
// Case mapping depends on the locale
console.log("I".toLowerCase(), "I".toLocaleLowerCase("tr"), "i".toUpperCase(), "i".toLocaleUpperCase("tr"), "ß".toUpperCase());
```

```
sort()          : Zoë, apple, item10, item9, zebra, Ähre, Émile, Østen
Collator de     : Ähre, apple, Émile, item10, item9, Østen, zebra, Zoë
Collator sv     : apple, Émile, item10, item9, zebra, Zoë, Ähre, Østen
numeric: true   : item1, item9, item10
---
length: 20 | [...s]: 15 | grapheme: 10
slice(0, 2): "👨"
café café === false | NFC === true | length 4 5
---
私 | は | フロント | エンド | を | 勉強 | し | てい | ます
---
i ı I İ SS
```

- Plain `sort()` puts `Zoë` before `apple` (uppercase comes first in the Unicode table) and every
  accented letter at the end. The German and Swedish collators disagree about `Ä` and `Ø`.
- A string that looks like 10 "letters" has a `length` of 20. `slice(0, 2)` cuts the family emoji
  and leaves only the father.
- Two `café`s that look identical aren't `===` until normalized.
- A Japanese sentence without spaces is split into words by `Segmenter`.
- `"ß".toUpperCase()` becomes two letters (`SS`), so a string's length can change when you change
  its case.

**4. RTL, logical properties, and `lang` in Chromium.**

```js
const { chromium } = require("playwright");
(async () => {
  const browser = await chromium.launch();
  const page = await browser.newPage({ viewport: { width: 400, height: 300 } });
  await page.setContent(`<!doctype html><style>
    body { margin: 0; font: 16px sans-serif; }
    .card { width: 300px; border: 1px solid; }
    .fisik  { margin-left: 40px; padding-left: 8px; text-align: left; }
    .logis  { margin-inline-start: 40px; padding-inline-start: 8px; text-align: start; }
    .panah { display: inline-block; }  /* transforms don't apply to plain inline elements */
    .panah:dir(rtl) { transform: scaleX(-1); }
  </style>
  <div dir="ltr"><div class="card fisik" id="ltr-fisik">Kartu</div><div class="card logis" id="ltr-logis">Kartu</div></div>
  <div dir="rtl" lang="ar"><div class="card fisik" id="rtl-fisik">بطاقة</div><div class="card logis" id="rtl-logis">بطاقة</div>
    <span class="panah" id="panah">→</span></div>
  <p lang="tr" id="tr" style="text-transform: uppercase">istanbul</p>
  <p lang="en" id="en" style="text-transform: uppercase">istanbul</p>`);
  const out = await page.evaluate(() => {
    const box = (id) => {
      const el = document.getElementById(id), r = el.getBoundingClientRect(), cs = getComputedStyle(el);
      return `left=${r.left} right=${400 - r.right} textAlign=${cs.textAlign} direction=${cs.direction}`;
    };
    return {
      "ltr fisik": box("ltr-fisik"), "ltr logis": box("ltr-logis"),
      "rtl fisik": box("rtl-fisik"), "rtl logis": box("rtl-logis"),
      panah: getComputedStyle(document.getElementById("panah")).transform,
    };
  });
  console.log(out);
  // innerText follows text-transform, so the per-language uppercase result is visible directly.
  console.log("tr:", await page.locator("#tr").innerText(), "| en:", await page.locator("#en").innerText());
  await browser.close();
})();
```

```
{
  'ltr fisik': 'left=40 right=50 textAlign=left direction=ltr',
  'ltr logis': 'left=40 right=50 textAlign=start direction=ltr',
  'rtl fisik': 'left=90 right=0 textAlign=left direction=rtl',
  'rtl logis': 'left=50 right=40 textAlign=start direction=rtl',
  panah: 'matrix(-1, 0, 0, 1, 0, 0)'
}
tr: İSTANBUL | en: ISTANBUL
```

(`fisik` = physical, `logis` = logical, `panah` = arrow.) In LTR the physical and logical cards sit
in the same place. In RTL the logical card moves to the right, 40 px from the right edge, an exact
mirror image. The physical card sticks to the right edge with no gap, its 40 px `margin-left` has no
effect, and its text stays left-aligned. The arrow gets `scaleX(-1)` only because it is inside
`dir="rtl"`. The same paragraph becomes `İSTANBUL` with `lang="tr"` and `ISTANBUL` with `lang="en"`.

Record your results and surprises in the [experiment notes](/en/notes/). Next challenge: add
`dir="rtl"` to this site's `<html>` in DevTools, then find which components still use physical
directions.

## Practical implications

- **Never format numbers, currency, or dates by hand.** Use `Intl`, and create one formatter per
  locale.
- **Translated messages must support every plural category.** Use ICU MessageFormat, not
  `count === 1`.
- **Sort with `Intl.Collator`**, and compare strings after `normalize("NFC")`.
- **Trim and count text by grapheme** (`Intl.Segmenter`), especially for input limits and usernames.
- **Send and store times as ISO 8601 with an offset;** calendar dates as `YYYY-MM-DD`. Always name a
  `timeZone` when displaying.
- **Write CSS with logical properties from the start.** Switching later costs far more than starting
  with them.
- **Set `lang` on `<html>` and on every part in another language,** and `dir` for RTL. Wrap user
  input in `<bdi>` or `dir="auto"`.
- **Test with pseudo-localization and one RTL locale** in CI or Storybook, not after translators are
  done.
